1. AI 에이전트가 뭔가요?
- 일반적인 챗봇은 질문을 받으면 바로 답변만 생성합니다. 
반면 AI 에이전트는 질문을 이해한 뒤 필요한 데이터를 찾고, 적절한 Workflow를 선택하고, 필요한 작업을 수행한 후 결과를 생성합니다. 
즉, 단순 답변이 아니라 업무를 수행하는 AI라고 볼 수 있습니다.

- 예를 들어 사용자가 "오늘 장애현황 보여줘"라고 질문하면 AI 에이전트는 먼저 장애 조회 요청인지 판단하고, 
운영 DB를 조회한 뒤, 장애 원인 분석과 우선순위 판단을 수행하여 결과를 제공합니다. 
이처럼 질문에 대한 답변뿐 아니라 필요한 작업을 스스로 수행하는 것이 AI 에이전트의 특징입니다.

2. LangChain인 뭔가요? 
LangChain은 LLM과 다양한 외부 시스템(문서, DB, API, Tool)을 연결하여 AI 애플리케이션을 개발하는 프레임워크입니다.

LLM 기반 AI 애플리케이션 개발을 위한 오픈소스 프레임워크입니다.
프롬프트, 외부 데이터, API, Tool 등을 LLM과 쉽게 연결할 수 있습니다.
RAG, Agent, 챗봇, 업무 자동화 시스템 개발에 많이 사용됩니다.
저는 LangChain을 활용해 ChromaDB 검색, 프롬프트 구성, LLM 호출 기능을 구현했습니다.

LangChain은 LLM과 RAG를 연결하는 역할로 사용했습니다. 
사용자의 질문이 들어오면 ChromaDB Retriever를 통해 관련 업무 문서를 검색하고, 검색 결과와 질문, 
시스템 프롬프트를 PromptTemplate으로 구성한 뒤 LLM에 전달하여 답변을 생성합니다. 
즉, Vector DB 검색, 프롬프트 생성, LLM 호출 부분을 LangChain으로 구현했습니다.

그래서 네가 발표할 때는 이렇게 말하면 된다.

LangChain은 LLM과 외부 시스템을 연결하는 프레임워크입니다. 사용자의 질문이 들어오면 ChromaDB, 운영 DB, E

즉 Retrieval된 데이터를 기반으로 LLM이 보다 정확한 답변을 생성하도록 구성했습니다.

3. LangGraph가 뭔가요?

  ├─ 배치 개발 workflow
  ├─ 장애 처리 workflow
  └─ 일반 fallback workflow

왜냐면 각 기능마다 필요한 처리 방식이 다르기 때문이야.

기능	처리 방식
업무 인수인계	RAG 검색 + 근거 기반 답변
SQL 분석	SQL 파싱 + 문제점 분석 + 개선안
배치 개발	요청서 해석 + 파일 생성 + 검증
장애현황	DB 조회 + 원인/조치 reasoning
청구 그래프	DB 조회 + 차트 렌더링 + 요약

그래서 네 구조처럼 상위 graph에서 route를 나누고, 각 기능별 workflow를 따로 두는 구조가 실제 업무에 더 가까워.

발표용으로는 이렇게 말하면 돼.

저희 시스템은 하나의 LLM 호출로 모든 질문을 처리하지 않고, 최상위 LangGraph에서 질문 유형을 먼저 분류합니다. 이후 업무 인수인계 질문은 RAG 기반 workflow로, 배치 개발 요청은 배치 생성 workflow로, SQL 요청은 SQL 분석 workflow로 분기합니다. 이렇게 기능별 workflow를 분리하면 운영 중 장애 원인 추적이 쉽고, 기능별 검증과 확장이 가능하기 때문에 실제 업무 시스템 구조에 더 적합합니다.

각 row별 상태/우선순위 판단
        ↓
표 + 요약 + reasoning 결과 출력


이 로그는 장애현황 질문을 처리할 때 어떤 workflow/step을 탔는지 기록한 것이야.

전체 흐름은 이렇게 처리된 거야.

사용자 질문: "장애현황 보여줘"
        ↓
질문 의도 판단: today_incidents
        ↓
실행 계획 로드: execution_plan_loaded = True
        ↓
선택된 단계:
1. prepare_realtime_query
2. status_reasoning
3. summarize_table
        ↓
장애 데이터 2건 조회
        ↓
각 row별 상태/우선순위 판단
        ↓
표 + 요약 + reasoning 결과 출력

각 로그 뜻은 이거야.

execution_plan_loaded = True
→ JSON에 정의된 실행계획을 정상적으로 읽었다는 뜻.

selected_steps = ['prepare_realtime_query', 'status_reasoning', 'summarize_table']
→ 장애현황 처리에 필요한 단계를 3개 선택했다는 뜻.

post_process = incident_reasoning
→ 조회 결과를 그대로 보여주는 게 아니라, 장애 판단 로직을 추가로 적용했다는 뜻.

target_domain = incident
→ 이 질문은 장애 도메인으로 처리했다는 뜻.

source_rows = 2
→ 장애 데이터가 2건 있었다는 뜻.

column_mapping = ...
→ 원본 컬럼명을 내부 판단용 컬럼으로 매핑했다는 뜻.
예: 배치명 → batch, 상태 → status, 경과분 → elapsed.

policy.long_running_minutes = 30
→ 30분 이상이면 장기 미처리로 판단하는 정책을 사용했다는 뜻.

reasoning_results = 2
→ 장애 2건에 대해 각각 reasoning 결과를 만들었다는 뜻.

priority_ranking = completed
→ P1/P2 같은 우선순위 산정이 끝났다는 뜻.

뒤쪽 로그는 Planner 쪽 로그야.

detected_request = today_incidents
→ 질문을 “오늘 장애현황 조회” 요청으로 분류함.

requires_reasoning = True
→ 단순 조회가 아니라 상태 판단이 필요하다고 봄.

requires_action_summary = False
→ 별도 조치 요약 step은 안 탐.

requires_impact_analysis = False
→ 영향도 분석 step은 안 탐. 그래서 영향도판단: -로 나온 거야.

selected_workflow = incident_reasoning_flow
→ 장애 reasoning용 workflow를 선택함.

row_reasoning = delegated_to_realtime_renderer
→ 각 장애 row별 판단은 renderer 쪽에서 처리했다는 뜻.

결론적으로 이건:

질문 분류 → 장애현황 workflow 선택 → 장애 데이터 조회 → 정책 기반 상태판단 → 우선순위 산정 → 표/요약 출력

으로 처리됐다는 로그야.

2. 왜 LangGraph를 사용했나?
답변

기능마다 처리 방식이 다르기 때문입니다.

예를 들어

=================
발표할 때는 너무 기술적으로 들어가지 말고 "왜 사용했는가" 중심으로 설명하는 게 좋습니다.

LangChain

LangChain은 LLM을 활용한 AI 애플리케이션을 개발하기 위한 프레임워크입니다.
사용자 질문, 프롬프트, 검색된 컨텍스트(RAG)를 결합하여 LLM에 전달하는 역할을 합니다.
저는 LangChain을 활용해 Vector DB 검색, 프롬프트 구성, LLM 호출 기능을 구현했습니다.

LangGraph

LangGraph는 AI Agent의 업무 흐름(Workflow)을 관리하는 프레임워크입니다.
질문 유형에 따라 업무 인수인계, 장애 조회, SQL 분석, 배치 개발 등의 Workflow로 분기하여 처리합니다.
이를 통해 하나의 LLM이 모든 질문을 처리하는 것이 아니라 업무별로 최적화된 처리 흐름을 적용할 수 있습니다.

ChromaDB

ChromaDB는 Vector DB로, 업무 문서를 임베딩하여 저장하고 유사도 검색을 수행합니다.
사용자 질문이 들어오면 관련성이 높은 업무 문서를 검색하여 LLM에 제공하는 RAG 구조를 구현했습니다.
이를 통해 LLM이 학습되지 않은 내부 업무 지식도 답변할 수 있도록 구성했습니다.

Multi-Step Reasoning

Multi-Step Reasoning은 복잡한 질문을 여러 단계로 나누어 처리하는 방식입니다.
예를 들어 장애현황 조회 시 단순 조회가 아니라 데이터 조회 → 원인 분석 → 우선순위 판단 → 조치 방법 요약 순으로 처리합니다.
이를 통해 단순 검색이 아닌 분석과 판단이 포함된 답변을 제공할 수 있습니다.

Harness Engineering

Harness Engineering은 AI Agent의 품질을 검증하기 위한 자동 테스트 체계입니다.
백엔드 개발의 Unit Test와 유사한 개념으로, 질문 시나리오를 기반으로 Intent 분류, 시스템 라우팅, Workflow, Tool 호출 등을 자동 검증합니다.
코드 변경 시마다 테스트를 수행하여 응답 품질이 유지되도록 구성했습니다.

LangSmith

LangSmith는 AI Agent의 실행 과정을 추적하고 분석하는 관측(Observability) 도구입니다.
각 Workflow의 입력값, 출력값, 토큰 사용량, 실행 시간, Trace를 확인할 수 있습니다.
이를 통해 병목 구간을 분석하고 성능 최적화 및 디버깅에 활용했습니다.

30초 요약 버전

LangChain은 LLM과 RAG를 연결하는 프레임워크이고, LangGraph는 업무별 Workflow를 관리하는 Agent 프레임워크입니다. ChromaDB는 업무 지식을 저장하는 Vector DB이며, Multi-Step Reasoning은 조회·분석·요약을 단계적으로 수행하는 추론 방식입니다. Harness Engineering은 AI 품질을 검증하는 자동 테스트 체계이고, LangSmith는 Agent의 실행 로그와 성능을 분석하는 관측 도구입니다.

======================
1. 왜 LangGraph를 사용했나요?

답변

업무 인수인계, 장애 조회, SQL 분석, 배치 개발은 처리 방식이 모두 다릅니다.
그래서 하나의 프롬프트로 처리하지 않고 LangGraph에서 질문 유형을 분류한 후 기능별 Workflow로 분기하도록 구현했습니다.

2. LangChain은 어떤 역할인가요?

답변

LangChain은 RAG 검색, 프롬프트 구성, LLM 호출을 담당합니다.
질문, 검색 결과(Context), System Prompt를 결합하여 LLM에 전달하는 역할을 수행합니다.

3. 왜 ChromaDB를 선택했나요?

답변

업무 문서를 벡터 형태로 저장하고 빠르게 검색하기 위해 사용했습니다.
또한 Metadata Filter를 지원하여 system_id, intent 기반 검색 범위를 제한할 수 있어 적합했습니다.

4. 업무 문서는 어떻게 적재했나요?

답변

업무 개요, 배치 프로세스, 배치 흐름도, 테이블 리니지 등 의미 단위로 분리한 후 JSON으로 구조화하여 ChromaDB에 적재했습니다.

5. Chunk 전략은 무엇인가요?

답변

문서를 통째로 넣지 않고 의미 단위로 분리했습니다.
길이가 긴 경우 Chunk Size와 Overlap을 적용하여 문맥 손실을 최소화했습니다.

6. 질문하면 실제로 어떻게 답변이 만들어지나요?

답변

질문 → 오타 보정 → Intent 분류 → System 식별 → Builder 생성 → Vector Search → Context 추출 → LLM 답변 생성 순으로 처리됩니다.

7. Builder가 무엇인가요?

답변

Builder는 검색 조건과 응답 형식을 생성하는 역할입니다.
검색 범위를 제한하고 결과를 표, 차트, 텍스트 등으로 제어합니다.

8. Multi-Step Reasoning은 무엇인가요?

답변

복잡한 질문을 여러 단계로 나누어 처리하는 방식입니다.
예를 들어 장애현황은 조회 → 원인 분석 → 우선순위 판단 → 조치 방법 생성 순으로 처리됩니다.

9. Planner Node는 무엇인가요?

답변

Planner는 질문에 필요한 처리 단계를 결정하는 역할입니다.
장애현황이면 조회, 분석, 요약 단계를 선택하고 Workflow를 구성합니다.

10. 장애현황은 RAG인가요?

답변

아닙니다.
장애현황과 청구 이용내역은 Realtime Query 기반입니다.
DB 조회 후 Multi-Step Reasoning으로 분석합니다.

이거 평가자들이 좋아함.

11. 왜 RAG를 사용했나요?

답변

LLM은 회사 내부 업무를 모르기 때문입니다.
내부 업무 문서를 검색해서 Context로 제공하기 위해 RAG를 사용했습니다.

12. 배치 개발은 어떻게 생성되나요?

답변

요청서를 분석하여 batch_spec을 생성하고 Template 기반으로 SQL, Python Job, Test Code를 자동 생성합니다.

13. 완전 자동 개발인가요?

답변

아닙니다.
약 70~80% 수준까지 자동 생성하고 나머지는 개발자가 검토 및 보완합니다.

이 답변이 훨씬 신뢰감 있음.

14. Harness Engineering은 왜 적용했나요?

답변

AI Agent도 일반 개발처럼 품질 검증이 필요합니다.
코드 변경 시 질문 시나리오를 자동 실행하여 응답 품질 저하를 방지합니다.

15. 어떤 항목을 검증하나요?

답변

System Routing, Intent 분류, 응답 유형, Workflow 흐름, Tool 호출, Multi-Step Reasoning 등을 검증합니다.

16. LangSmith는 왜 사용했나요?

답변

Agent 실행 과정을 추적하고 병목 구간을 확인하기 위해 사용했습니다.
입력값, 출력값, 토큰 사용량, 실행 시간 등을 확인할 수 있습니다.

17. 토큰이 왜 중요한가요?

답변

토큰이 많아질수록 응답 시간이 증가하고 비용도 증가합니다.
그래서 Context 크기와 Retrieval 결과를 최적화하여 관리했습니다.

18. 오픈소스 LLM은 사용했나요?

답변

개발 초기에는 Upstage LLM을 사용했고, 이후 AWS EC2 환경에 Qwen 모델을 vLLM으로 서빙하여 테스트했습니다.

19. 실제 업무에 적용 가능하다고 생각하나요?

답변

가능합니다.
업무 지식 검색, 장애 분석, SQL 분석, 배치 개발 지원 등 반복적인 업무를 자동화할 수 있으며 신규 인력 온보딩에도 활용 가능합니다.

20. 이 프로젝트의 핵심 차별점은 무엇인가요?

이건 거의 마지막 질문으로 나온다.

답변

단순 챗봇이 아니라 금융 업무 지식을 구조화하여 RAG, Workflow Routing, Multi-Step Reasoning, Harness 검증 체계를 결합한 실제 업무 지원형 AI Agent를 구현한 것이 핵심입니다.

이 20개 정도만 준비하면 평가자가 물어볼 질문의 90% 이상은 커버 가능해. 특히 5번(Chunk), 8번(Multi-Step), 14번(Harness), 20번(차별점) 은 반드시 준비하는 게 좋아.
