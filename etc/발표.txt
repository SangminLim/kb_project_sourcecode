에이전트 핵심기능
에이전트 기능1 - 업무 개요 분석 에이전트
금융 업무 개요, 주요 처리 흐름, 입력/출력 데이터를 자연어 기반으로 설명

에이전트 기능2 - 배치 프로세스 분석 에이전트

배치 Job 흐름 및 선후행 관계를 분석하여 프로세스 설명 및 시각화 제공
에이전트 기능3 - 테이블 리니지 분석 에이전트
테이블 간 데이터 흐름 및 JOIN 관계를 분석하여 리니지 시각화 제공

에이전트 기능4 - 장애 분석 에이전트
장애 로그 및 오류 유형 기반으로 원인 분석 및 조치 방법 자동 추천

에이전트 기능5 - SQL 운영 분석 에이전트
SQL Full Scan 여부, Index 활용, Partition 조건 누락 등을 자동 분석

에이전트 기능6 - 배치 개발 지원 에이전트
배치 요청서를 기반으로 SQL 및 배치 스펙 초안 자동 생성

발표에서는 이렇게 말하면 돼:

“PoC 단계에서는 로컬 노트북 성능 한계로 인해 Upstage Solar LLM API를 활용했습니다. 다만 에이전트 구조는 LangGraph, LangChain, RAG, Vector DB 중심으로 분리 설계하여 향후 금융권 운영 환경에서는 내부망 GPU 서버와 오픈웨이트 LLM로 전환 가능하도록 구성했습니다.”

핵심은 이거야:

구분	발표 표현
지금	Upstage Solar LLM API 사용
이유	로컬 노트북 환경에서 오픈웨이트 LLM 구동 시 응답 지연 발생
보완	LLM 호출부를 추상화해서 교체 가능 구조
향후	내부망 GPU 서버 + vLLM + 오픈웨이트 LLM 전환 가능

즉, **“오픈소스를 못 써서 부족하다”**가 아니라
“PoC는 API로 빠르게 검증하고, 운영은 내부망 LLM로 전환 가능한 구조로 설계했다”고 말하면 돼.

발표자료에는 이렇게 넣자:

LLM 구성 전략

현재 PoC 단계에서는 로컬 개발 환경의 GPU 성능 한계와 빠른 기능 검증을 고려하여 Upstage Solar LLM API를 활용하였다.

다만 에이전트의 핵심 구조는 LangGraph Workflow, LangChain RAG, Vector DB, Retriever, Prompt Template을 분리하여 설계했기 때문에 LLM Provider 교체가 가능하다.

향후 금융권 운영 환경에서는 내부망 GPU 서버에 오픈웨이트 LLM을 배포하고 vLLM 기반 모델서빙 구조로 전환할 수 있다.
